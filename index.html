01역량

팀이 하는 일

20년 경력의 개발자들이 규모와 분야에 맞춰 설계부터 배포까지 함께합니다. 공개할 수 있는 사례는 지금 artdg.com 1건이어서, 아래 근거는 모두 그 사례에서 가져왔습니다.

  1. 01

    웹 서비스 구축 (커머스)

    상품을 찾고, 수량을 계산해 장바구니에 담는 쇼핑몰을 만듭니다.

    1. 카탈로그·검색
    2. 규격·가격 표시
    3. 수량 계산
    4. 장바구니

    근거 artdg.com은 상품 135개, 분류 37개를 규격·가격·묶음 단위로 보여 줍니다.

  2. 02

    관리자·백오피스

    운영자가 관리자 화면에서 상품과 규칙을 바꾸고 발행하는 구조를 만듭니다.

    관리자 · 구매 규칙 · 읽기만 함

    근거 상품·옵션, 구매 규칙, 묶음 할인, 배송, 분류를 편집하고 초안을 거쳐 발행합니다. 가격 인하 1회 25% 이내, 변경 감사 기록, 버전 충돌 방지가 있습니다.

  3. 03

    데이터 이관·재구축

    옛 사이트의 데이터를 새 구조로 옮기며 다시 만듭니다.

    근거 artdg.com은 옛 그누보드/영카트 DB의 상품 135개를 옮겨 다시 만든 사이트입니다. 처음부터 새로 만든 사이트가 아닙니다.

  4. 04

    결제 연동

    결제 서비스 연동을 검수 환경까지 진행합니다. 지금은 검수 단계입니다.

    • 검수 중네이버페이: 연동 중(sandbox 검수 단계)
    • 미구현취소·반품·교환, 주문 상태 동기화

    근거 운영 주문 등록은 승인 전까지 닫혀 있고, 실제 결제 완료는 확인하지 않았습니다.

  5. 05

    운영·배포 자동화와 테스트

    Cloudflare Workers와 D1 위에서 실행하고, 테스트와 운영 문서를 함께 둡니다.

    • 자동 테스트
    • E2E 테스트
    • 배포 가드
    • 운영 문서(RUNBOOK)

    근거 artdg.com 저장소에 위 4가지가 있습니다. 저장소는 비공개입니다.

  6. 06

    설계·성능

    52~170ms

    근거 artdg.com 상품정보 응답 시간입니다. 값은 스키마 기반으로 편집합니다.

그 밖에 다루는 일

공개 사례는 지금 artdg.com 1건이어서, 아래 분야는 문의하시면 범위에 맞춰 설명드립니다.

  • 데이터 수집·정제웹과 API에서 데이터를 모으고, 쓸 수 있는 형태로 정리합니다.
  • 업무·반복 작업 자동화사람이 반복하는 작업을 스크립트와 스케줄로 바꿉니다.
  • 백엔드·API 개발서비스의 서버와 데이터 구조를 설계하고 구현합니다.
  • 외부 시스템·API 연동결제, 배송, 사내 시스템 같은 외부 서비스와 연결합니다.
  • 클라우드 배포·운영배포 자동화, 모니터링, 장애 대응 절차를 갖춥니다.
  • 기존 서비스 개선·유지보수동작 중인 서비스의 속도, 구조, 기능을 고칩니다.
02설계

구조와 설계 결정

기능이 아니라 구조로 일합니다. 아래는 공개 사례 artdg.com이 실제로 돌아가는 구조와, 그렇게 정한 이유입니다.

운영 값을 바꾸는 쪽

  1. 관리자접근 제한 + 서버에서 토큰 재검증
  2. 설정 저장소 (D1)초안 · 변경 이력 · 버전
  3. 발행 절차검증 후 정적 파일 생성

공개 방문자가 보는 쪽

  1. 콘텐츠 정본 (JSON)상품·분류·안내·규칙
  2. 정적 사이트 (Next.js)빌드 시점에 화면 생성
  3. Cloudflare Workers정적 파일 배포

주문 별도로 분리된 쪽

  1. 브라우저장바구니는 기기에만 저장
  2. API Worker주문 등록 · 상품정보 응답
  3. 네이버페이검수 중 (sandbox)

  1. 공개 화면과 주문 처리를 나눴습니다

    화면은 정적 파일이라 빠르고 장애 범위가 좁습니다. 주문 API가 없으면 구매는 닫힌 상태로 유지됩니다. 실패해도 잘못 열리지 않는 쪽으로 기울였습니다.

  2. 관리자는 한 겹 더 막았습니다

    접근 제한 뒤에 두고, 서버에서도 토큰을 다시 검증합니다. 주문 접수를 한 번에 끄는 스위치가 있습니다.

  3. 값을 바꾸는 절차를 남겼습니다

    저장은 초안이고, 발행해야 사이트에 반영됩니다. 변경 이력이 남고, 두 곳에서 동시에 고치면 한쪽이 덮어쓰지 못하게 버전으로 막습니다.

  4. 가격 기준을 한 곳에 뒀습니다

    판매 판정, 관리자 입력, 주문 데이터가 같은 하한(원본가 50%)을 씁니다. 인하는 1회 25% 이내입니다. 기준이 화면마다 달라지는 사고를 막기 위해서입니다.

  5. 중복 주문을 막았습니다

    같은 구매 시도에는 같은 키를 붙이고, 탭이 여러 개여도 등록을 한 번에 하나씩 처리합니다. 결과가 불확실하면 다시 시도하지 않고 확인을 안내합니다.

  6. 배포 실수를 먼저 막았습니다

    뒤처진 코드나 커밋하지 않은 변경이 있으면 배포가 시작되지 않습니다. 단위·계약 테스트와 화면 E2E 테스트, 운영 문서가 함께 있습니다.
